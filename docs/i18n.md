# Internationalization (issue #236)

v1 goal from the issue: **one JSON per language, translated from a base JSON, provider-ready**, with
no translation-provider integration yet.

## Runtime JSON, not `@angular/localize`

`@angular/localize` is **compile-time**: one build per locale. This project ships a PWA plus
Capacitor and Electron shells that all wrap the *same* `@nicotind/web` build, and releases are
frequent. N builds per release, N service-worker payloads and no live language switch is the wrong
trade here.

Runtime JSON keeps **one build**, switches language without a reload, and leaves the catalog as a
plain keyed file a provider (POEditor/Crowdin) can export/import later — exactly the issue's stated
recommendation.

**No library either.** `@ngx-translate/core` would do, but the whole surface needed is "look a key
up in a JSON object and interpolate `{placeholders}`" — that is `services/translate.service.ts`.
Same call the repo already made for charting (an inline SVG radar over a chart dep), and the
initial bundle is already under scrutiny (issue #256). Swapping in a library later changes this
service, not the call sites.

## How it works

- `public/i18n/en.json` is the **base and source of truth**; `es.json` is a sibling.
- `TranslateService.init()` runs from `provideAppInitializer`, **not awaited** — a slow or failed
  catalog fetch must never delay or block bootstrap.
- Lookup falls through **active → base → the key itself**. So a partially translated language shows
  English for its gaps rather than raw keys, which is what makes incremental translation safe; and
  a key missing everywhere renders visibly (it gets noticed and fixed) rather than blank.
- `{{ 'login.submit.signIn' | t }}` at call sites; `t()` also takes `{name}` params.

## The pipe is impure, and that was measured

The obvious design is a **pure** pipe relying on `t()`'s signal reads to re-render on a language
switch. **It does not work**, and the spec caught it: a pure pipe memoizes on its arguments, so
when only the language changes `transform` is never called again and the signal is never read — the
UI keeps the old language. A direct `{{ i18n.t('key') }}` call *does* react (also measured) but
costs the same per change-detection pass while being less ergonomic.

So the pipe is `pure: false`, made cheap by memoizing on **(key, language, params)**: the
per-change-detection work is a string compare and an early return.

`translate.service.spec.ts` asserts the switch reaches the DOM. Don't "optimise" the pipe back to
pure without re-running it.

## Language selection is per-device

`localStorage` (`nicotind-lang`), defaulting to `navigator.languages` matched on the **base**
language (`es-AR` → `es`), else English. Per-device rather than per-user on purpose: the login,
setup and public share pages all render **before any user exists**, and a per-user setting would
leave exactly those pages untranslatable. A `user_settings` mirror is a follow-up, not a
replacement.

The picker lives in Settings → Appearance (`data-testid="settings-language"`).

## Coverage so far, and how to extend

The issue plans extraction as a **phased mechanical pass**. Converted so far:

1. The **login page** (the proof surface — it renders pre-auth, which is also why storage is
   per-device) and the picker's own strings.
2. The **app shell** — both navs and the offline banner. Nav labels live in a **TS array**, not a
   template, so `label` now holds an i18n **key** rendered through the pipe. That shape change is
   why `bottom-nav.component.spec.ts` asserts keys *and* checks each one resolves against the real
   `en.json`: asserting the key list alone would let a typo render a raw key and still pass.
3. The **library tabs + sort options** — the main content surface, same
   TS-array-holds-a-key shape.
4. The **home page** (the post-login route) — vibe presets and section headings.
5. The **Acquire page** (`pages/search/`, renamed from Search per #227) — its
   primary copy under the `acquire.*` namespace: the search placeholder + submit,
   recent-searches, source status (`acquire.sources` uses `{list}` interpolation),
   the Albums/Artists/Results headers, the Get / Added labels, the idle empty
   state, and the acquisition-off state. The deep folder-browser / power-user
   strings inside the collapsed **Advanced** disclosure are intentionally left for
   a later slice — they are low-traffic and behind a disclosure.
6. **Player + Now Playing + Settings** (the phase-2 high-traffic slice) — the
   `player.*` (mini-player autoplay banner + the "unavailable offline" toast),
   `nowPlaying.*` (the full sheet: header, lyrics states, transport, queue,
   fullscreen karaoke overlay), and `settings.*` namespaces (every section
   header, toggle label/hint, the remote-playback/device-name/server/account/
   desktop/iOS-diagnostics sections, and the sign-out confirm dialog). The iOS
   diagnostics `<dl>` labels (`plugin registered`, `session configured`, …)
   stay English on purpose — a developer-facing technical dump, not listener
   copy, and not worth the key overhead. Pluralization for "N tracks saved" /
   "remove N auto-saved tracks" uses the plain `count === 1 ? …One : …Other`
   branch already established for pluralized keys (no ICU).
7. **Devices / remote-access settings** (`pages/settings/devices/`, issue #338 — the first slice of
   the long-tail follow-up) — the `devices.*` namespace: the pairing panel (QR alt text, expiry
   countdown, manual-entry code, generate/regenerate), paired-devices list (revoke, "this device",
   the `{platform} · linked … · last seen …` meta line), and the admin-only Tailscale Funnel guided
   state machine (all six `RemoteAccessState` branches — not-installed/needs-login/needs-operator/
   funnel-not-enabled/active/inactive/error — plus the three error toasts). The "Scan with your/the
   other phone's camera — or … Scan QR …" sentence, which embedded two bold inline spans, was
   collapsed into two full-sentence keys (`scanInstructionsYour`/`scanInstructionsOther`) rather
   than stitched from fragments around a translated `{device}`/`camera` — correct interpolation
   order isn't guaranteed across languages (Spanish naturally reorders "cámara" before "del otro
   teléfono"), so a full sentence per branch is the only shape that translates correctly, at the
   cost of losing the mid-sentence bold emphasis. Added a shared `common.backToSettings` key for the
   "← Settings" back-link (reused verbatim by `agent-tokens`/`plugins` pages, both still English —
   next slices will pick it up when those pages convert).
8. **Onboarding / setup wizard** (`pages/setup/`, issue #338) — the `setup.*` namespace across all
   five steps (admin account, music library, streaming quality, Soulseek + the Advanced Lidarr
   disclosure, done screen), plus two more `common.*` keys (`back`/`next`, alongside
   `common.backToSettings`). `setupComponent`'s error toast was also switched onto
   `httpErrorMessageI18n` (the #337 helper) instead of reading `err.error?.error ?? err.message`
   directly — the same non-`HttpErrorResponse` shape login.component.ts already stopped trusting.
9. **Admin panel** (`pages/admin/`, issue #338) — the biggest single-page slice so far, 215 new
   `admin.*` keys covering every section (system status, library processing task list, streaming,
   backups, audit log, user management, auto-playlists, duplicates, orphan rows, artist-image
   coverage, acquisition toggle). `processingTaskDefs` (the per-task checkbox list) changed from a
   pre-translated `label` field to a `labelKey`, so a live language switch re-renders the task names
   through the template's `| t` pipe like everything else on the page, instead of freezing at
   whatever language was active when the array was constructed. Left untranslated: codec/format
   names (proper nouns), and raw data values (usernames, table names, timestamps, server-reported
   job states) — not copy, just data rendered through the same row.
10. **Acquire page's Advanced disclosure** (`pages/search/`, issue #338) — the last long-tail slice,
    closing the issue. Converts the collapsed "browse Soulseek peers & folders" power-user section:
    the toggle + summary counts, the searching/stop/no-results states, the Songs/Folders view
    toggle + download-all, per-song and per-folder-file `Open`/`Download` labels, the folder-tree
    "Load/Hide full tree" toggle, and the lossless→Opus tooltip (also applied to its one other
    occurrence in the primary, non-Advanced Results section, since it's the exact same string).
    **Deliberately NOT touched**: the `getFolderBtn`/`getSongBtn`/`getGroupFileBtn` status-label
    helpers (`Get`/`Downloading N%`/`Queued`/…) — these come from shared library functions

That covers the always-on-screen surfaces, the first three high-traffic pages (the third split
across Player/Now-Playing/Settings), and every slice of the #338 long tail (devices, setup, admin,
Acquire Advanced) — **issue #338 is closed**. **es.json is at full parity** with the base (every en
key translated), verified by the i18n e2e's orphan check; a future page adding keys should translate
them in the same pass or accept the English fallthrough. The one open follow-up is the shared
download-status-label vocabulary noted above, which spans multiple components and isn't a single
page's slice.

### Calling `t()` from TypeScript, not just the template

Toasts and other messages built in a component's `.ts` (not through the `t` pipe in a template) call
`TranslateService.t(key, params)` directly — the first place this repo does that is
`player.component.ts` (the offline-unavailable toast) and `settings.component.ts` (the update-check
toasts, the auto-preserve confirm dialog, the auto-preserve explainer, the music-dir restart-failure
fallback). The convention is one `private i18n = inject(TranslateService)` per component and a
direct `this.i18n.t('some.key', { param })` call at the message-construction site — no new
abstraction on top of what `TranslatePipe` already does internally.

**A key can deliberately be identical across catalogs.** `vibe.fast` is
`120bpm+` in both: a bpm threshold reads the same in Spanish. Keep the key
rather than omitting it — omitting makes it fall back to English *silently*,
which is indistinguishable from an untranslated string, whereas an identical
value records that someone decided.

**A failed lookup renders as its dotted key**, which is deliberately conspicuous, so the e2e
asserts the *absence* of a key prefix (`library.tab.`) in the rendered tabs as well as the presence
of the translation. That catches a typo'd key, which a presence-only assertion would not.

⚠️ **When adding the pipe import to a component, place it after a COMPLETE import statement.**
Scripted insertion "after the last line starting with `import`" lands *inside* a multi-line import
block and produces a syntax error that `tsc --build` reports as a cascade of unrelated parse
errors. This has now bitten twice in this repo.

To convert a surface: add keys to `en.json` (+ any translations), import `TranslatePipe`, replace
the literal with `{{ 'key' | t }}`. An e2e asserts every `es.json` key exists in the base, so a
stray key that no provider export could map fails CI.

## Server error codes — client mapping started (issue #337)

Server-originated error responses now carry a stable, machine-readable `code` field alongside the
existing English `error` string (additive — `{ error, code }`, never a breaking shape change).
`@nicotind/core`'s `NicotinDError` hierarchy already had `code` (`AUTH_ERROR`, `NOT_FOUND`, …); this
pass extended the same field onto the inline `c.json({ error, ... })` responses in the routes a
logged-in session actually reaches at auth time and from the Settings page — `routes/auth.ts`
(`REGISTRATION_DISABLED`, `USERNAME_TAKEN`, `INVALID_CREDENTIALS`, `ACCOUNT_DISABLED`,
`SHARE_SESSION_NO_REFRESH`, `DEVICE_REVOKED`), `routes/devices.ts` (pairing/claim flow:
`RATE_LIMITED`, `VALIDATION_ERROR`, `PAIRING_NOT_FOUND`, `PAIRING_EXPIRED`, `ACCOUNT_DISABLED`,
`NOT_FOUND`), `routes/settings.ts` (the slskd extension config routes reachable from Settings:
`FORBIDDEN`, `VALIDATION_ERROR`, `SERVICE_UNAVAILABLE`, `INTERNAL_ERROR`), and `routes/agent-tokens.ts`
(`VALIDATION_ERROR`, `NOT_FOUND`). The other ~24 route files' inline errors are untouched — this is
explicitly a scoped slice, not a repo-wide migration.

**The client now maps a subset of these codes to i18n keys** (`lib/http-error.ts`
`ERROR_CODE_I18N_KEYS`), but deliberately not all of them: only codes whose English message is the
**same string everywhere they're returned** get a translation (`REGISTRATION_DISABLED`,
`USERNAME_TAKEN`, `INVALID_CREDENTIALS`, `ACCOUNT_DISABLED`, `PAIRING_NOT_FOUND`, `PAIRING_EXPIRED`,
`RATE_LIMITED`). Generic codes like `VALIDATION_ERROR`/`FORBIDDEN`/`NOT_FOUND`/`INTERNAL_ERROR`/
`SERVICE_UNAVAILABLE` carry a *different* message per call site (`"name is required"` vs.
`"path is required"`, `"Device not found"` vs. `"Token not found"`), so mapping them to one fixed
string would be wrong at most sites — those fall through to the raw (untranslated, English) server
message, same as before this pass.

Two small helpers in `lib/http-error.ts` do the lookup: `errorMessageForCode(code, i18n, fallback)`
for callers that already extracted a `code` some other way (e.g. a plain-`fetch` flow that isn't
`HttpErrorResponse`), and `httpErrorMessageI18n(err, i18n, fallback)` — the localized counterpart to
the existing `httpErrorMessage` — for HttpClient error handlers. Converted call sites:
`login.component.ts` (login/register errors), the `/pair` claim flow (`lib/pairing.ts`'s
`claimPairing` now throws a `PairingClaimError` carrying `code`, consumed by `pair.component.ts` and
`server-config.component.ts`'s scan/manual-code claim), and `auth.interceptor.ts`'s force-logout-on-
account-disabled check — which used to string-match the English `error` body (`=== 'Account
disabled'`), a latent bug the moment that string changed or the response was ever localized; it now
checks `code === 'ACCOUNT_DISABLED'`.

**Still not converted**: the Settings/Admin/devices-management error toasts (their codes are mostly
the generic, non-mappable ones above), and `DEVICE_REVOKED`/`SHARE_SESSION_NO_REFRESH` (no web call
site displays them today — the silent-refresh failure path just logs out; adding an i18n key with no
reader would be exactly the premature indirection this repo avoids). Extend
`ERROR_CODE_I18N_KEYS` + convert a call site together, one at a time, as each concretely needs it.

## Open, deliberately

- **The rest of server-originated strings** (onboarding copy, the ~24 untouched route files' inline
  errors) are still plain English with no `code`.
- **Client-side use of the new `code` field** — deferred, see above.
- **Pluralization/ICU** — `{count}` interpolation + a manual `…One`/`…Other` key branch for now; no
  real plural-rule engine (irrelevant for the two languages shipped so far, but won't scale to
  languages with more plural forms).
- **Which languages** beyond `es`.

# NicotinD Acquisition Addon Protocol — v1 (public reference)

This is the contract a third-party addon speaks. An addon is an HTTP service;
NicotinD ("core") registers it by URL + bearer token and consumes it through
this protocol. Core never runs addon code — the entire boundary is HTTP.

**Machine-checkable schema:** [`v1/schema.json`](./v1/schema.json), generated from
core's Zod DTOs (`@nicotind/core`). Validate your request/response payloads
against its `$defs`. Regenerate with
`bun run packages/core/src/scripts/gen-addon-schema.ts`.

## Versioning policy

- One `protocolVersion` (semver) governs the whole protocol.
- **Additive-only within a major**: new optional fields, capabilities, and
  endpoints may appear in a minor; a field or capability may be marked
  deprecated in a minor but is **removed only in a major**.
- **Breaking changes bump the major.** Core declares the majors it supports
  (`SUPPORTED_PROTOCOL_MAJORS`); an addon outside that range is refused at
  registration and disabled at boot with a stated reason.
- Build against a major, not a patch: any `1.x` addon works with any `1.y` core.

**1.1** added one optional response field: `AddonJob.title`, a human display name
for the job (the playlist name, the video title, the release name). It is
**display-only and never filing metadata** — `AddonJob.album` becomes the core
row's `album_title`, which mints an album id and tells the organizer where the
files go, so a playlist name there would create a phantom album and mis-file
every track in it. A 1.0 addon that omits `title` is unaffected: core falls back
through its own title chain (destination album → source folder → the pasted URL →
the source label). Job responses are not schema-validated, so no published
`$defs` changed.

## Capabilities

An addon's `manifest.capabilities` are both what it can do and what the admin
consents to. Core uses the **intersection** of what the addon declares and what
this core version implements; a capability core does not recognize is ignored
(forward-compatible), and an addon that declares *nothing* core can use is
refused. Current acquisition capabilities:

| capability | meaning |
| --- | --- |
| `search` | blended song/folder search |
| `browse` | list a peer's files/folders |
| `resolve` | resolve a URL to downloadable media (reserved; not yet consumed) |
| `download` | run jobs that deliver files core ingests into the library |

Each capability's plain-language consent line lives in
`@nicotind/core` `addon-capability-risk.ts` and is shown to the admin at enable.

## Endpoints (`/addon/v1/…`)

`GET manifest` and `GET health` are unauthenticated; everything else requires
`Authorization: Bearer <token>`.

| endpoint | purpose |
| --- | --- |
| `GET manifest` | self-description (see `$defs.Manifest`) |
| `GET health` | `{ ok, ready, detail? }` |
| `GET status` | typed status rows for the generic panel |
| `PUT config` | core pushes config the manifest declared |
| `POST search` | `$defs.SearchRequest` → blended results |
| `POST albums/search` | `$defs.AlbumSearchRequest` → scored folder candidates |
| `POST jobs` (+ `Idempotency-Key`) | `$defs.JobRequest` → a job |
| `GET jobs?since=` / `GET jobs/:id` | job + item state (stable `itemId`) |
| ↳ `AddonJob.title` (1.1, optional) | human display name — the playlist name, the video title, the release name |
| `POST jobs/:id/cancel` · `DELETE jobs/:id` | control |
| `GET jobs/:id/files/:itemId` | deliver a completed file's bytes |
| `GET browse?user=` | folder browser |
| `POST notify/library-changed` | core tells a sharing addon the library changed |

### Resolve (downloader) addons — report what the source reported

A `url` job is judged by its **items**, so an addon that only globs the files it
finds cannot tell the host about a partial result. Emit one item per track the
source announces, in the order it announces them (`downloading` → `completed`
with `fileReady`), and when the source stated a total (a playlist of 16) but
reported fewer, add the remainder as `unavailable` items. Close the job `partial`
with the real error text when some tracks landed and `failed` when none did.
Put the playlist/video title in `AddonJob.title` (1.1) as soon as you know it —
the host renames the card on its next poll. The parsers for yt-dlp's and spotDL's
stdout ship in the SDK (`downloader-output.ts`).

## Security limits core enforces (know these — your addon lives inside them)

Core treats every addon response as untrusted input:

- **JSON responses are capped at 8 MiB** and must be `application/json`; an
  oversized, non-JSON, or malformed body is rejected (the call fails, core stays
  up). Keep manage/observe payloads small.
- **A delivered file is capped at 2 GiB** and streamed with the cap enforced;
  its filename is reduced to a basename and contained to core's staging dir (no
  path traversal).
- **URLs your responses hand core to fetch** (e.g. a cover URL) are SSRF-guarded:
  `http(s)` only, and private/loopback/link-local targets are refused.
- **Repeated contract violations disable your addon** (a circuit-breaker);
  transient failures (timeout/5xx) do not. Return well-formed responses.

## Consent & trust posture

Registration is admin-only; the admin vouches for the URL. Core's defenses are
defense-in-depth against a mistaken or compromised addon, not a sandbox for a
fully-weaponized one. See
`docs/superpowers/specs/2026-08-13-addon-ecosystem-security-contract-foundation-design.md`
for the full design.

# Design patterns — detail for patterns without a dedicated doc

`CLAUDE.md` carries a one-line index of every design pattern. The **detail** for each
pattern lives either in a dedicated `docs/<feature>.md` (see the pointer table below) or,
for patterns that don't warrant their own file, **in full here**. This keeps the
per-request `CLAUDE.md` small while keeping the rationale discoverable.

> **Documentation rule:** when you add or change behavior, update the detail (here or in
> the dedicated doc) **and** the one-line index entry in `CLAUDE.md` in the same change.
> Don't grow a dense multi-sentence bullet back into `CLAUDE.md`. Stale docs are a bug.

## Patterns documented here (no dedicated doc)

- **Lyrics (on-demand, plugin-sourced, editable)**: lyrics are fetched on demand from a **lyrics source plugin** and persist + can be user-edited. This added a **new `metadata` plugin kind** with a **`lyrics` capability** (`@nicotind/core` `plugin/{manifest,capabilities,index}.ts`: `LyricsCapability.fetchLyrics(LyricsQuery)→LyricsResult|null`; `validatePluginManifest` allows `lyrics` for `metadata` and **scopes the `defaultEnabled:true` ban to `acquisition` only** so a benign keyless source can default-on) — the documented "add a kind" recipe; the registry kernel is unchanged. First source: the **LRCLIB plugin** (`services/plugins/lrclib/`, pure-JS `fetch`, no key, returns both plain + synced LRC; `/api/get` exact match → `/api/search` fallback; injectable `fetchFn`), registered + `seedEnabled('lrclib',…)` in `index.ts` so it activates on first boot. **Transient failures are retried** (`request()` retries up to 3× with a short backoff on 429/5xx/network/timeout; a **404 short-circuits** as an authoritative no-match) — without this a throttled/timed-out *first* request surfaced as a false "no lyrics found" and the user had to click "Fetch lyrics" 2–3× before a warm request succeeded (`retryBackoffMs` is injectable so tests don't wait). Storage is the **`library_lyrics` side-table** keyed on the path-derived `songId` (`lyrics-store.ts`; `plain_text`/`synced_text`/`source`/`customized`/`updated_at`); plain text is **also written back to the file tag** (`audio-tags.ts` now writes/reads **ID3 USLT** + **Vorbis `LYRICS`**, like BPM) so it survives a move/transcode (synced LRC stays DB-only — no clean embedded standard). Routes (`routes/library.ts`, registry threaded via `LibraryRoutesOptions.pluginRegistry`): `GET …/lyrics` (any user → `LyricsDto`|null), `POST …/lyrics/fetch` (any user — keyless/benign; **returns a cached row unmodified**; on a DB miss it first **recovers lyrics from the file tag** (`source:'file-tag'` — the orphaned-row-after-transcode path), else queries `getEnabledWithCapability('lyrics')`, persists the first hit + writes the tag; **a `customized` user edit is never clobbered unless `force:true`**; `503` when no lyrics source enabled; **`502` when a source *errored* vs `null` for a confident no-match** — the route tracks whether any plugin threw so a transient failure surfaces as a retryable error instead of a false "no lyrics"), `PUT …/lyrics` (admin — sets `customized=1`, `source='user'`, **clears synced** since an edited body no longer matches its timing), `DELETE …/lyrics` (admin reset). Web: the `track-info-sheet` drawer's **Lyrics section** (`data-testid="lyrics-section"`, fetch/`edit`("Add" when empty)/save/reset) and the **now-playing lyrics panel** (a **Lyrics tab** alongside Queue — `NowPlayingPanelTabsComponent`, `data-testid="now-playing-tab-lyrics"`, see the Now Playing component-split entry in [docs/web-ui.md](web-ui.md) — replaced the old lyrics-toggle-swaps-the-queue model) renders a **karaoke-styled** panel that **highlights the active synced line** via the pure `lib/lrc-parser.ts` `parseLrc`/`findActiveLine` driven by `player.currentTime()`, with auto-scroll, fading-edge mask, and a scale-1.05 active line; falls back to scrollable plain text). The **empty state is a centered styled block** (`now-playing-lyrics-empty`) with a note icon and an inline **Fetch lyrics** button (`fetchLyricsManually()` force-fetches; `now-playing-lyrics-fetch`); a source failure (502) flips it to a distinct "Couldn't reach the lyrics source — Try again" via the `lyricsError` signal (vs a confident "No lyrics found"). A **fullscreen button** (`now-playing-karaoke-toggle`) expands the lyrics into an immersive gradient-covered overlay with glow orbs (palette extracted from cover art via `lib/cover-colors.ts`) and dedicated transport controls. **The fullscreen body defaults to a 2-line auto-follow view** (current line + next line only, `karaokeBrowsing` signal false) so long lyric lines never wrap/crowd a narrow TV or monitor window — a slide+crossfade CSS keyframe animation (`karaoke-line-anim-a`/`-b` in `styles.css`, alternated by name to force a replay) plays on every line advance. A wheel/touch gesture on the lyrics body (`onKaraokeInteraction`) switches to **browse mode**, restoring today's full masked-scroll list with tap-to-seek (`seekToLine(index)`, reuses `onSeek`); browse mode auto-returns to the 2-line view after 4s idle or immediately after a seek. **Synced-line behavior (both modes) is unit-test-only** — there is no e2e-safe way to seed `synced` LRC (`PUT …/lyrics` always clears it on a user edit); e2e covers only the plain-text fallback path, asserting the `karaoke-fullscreen-follow` block is absent when lyrics are unsynced (`karaoke-fullscreen-line-current`/`-line-next`/`-browse-list` are unit-tested only, per the limitation above). **Browse mode is also keyboard/TV-remote reachable**: ArrowUp/ArrowDown on the focused overlay (auto-focused on entry) or the header's "browse lyrics" toggle button (`karaoke-browse-toggle`) call the same `onKaraokeInteraction()` / `toggleKaraokeBrowsing()` path as the wheel/touch gesture, and browse-list lines are `tabindex="0"`/`role="button"` with Enter/Space wired to `seekToLine`. **All lyrics surfaces are horizontal-overflow-safe**: every line/`<pre>` carries `break-words` and its scroll container is `overflow-x-hidden`. The fullscreen scroller adds `px-4` so the **active line's `scale-105` transform** paints into the padding instead of spilling past the viewport edge. Guarded by the `mobile-ux` e2e "long lyrics wrap and do not overflow horizontally". `LyricsDto` lives in `@nicotind/core` (+ re-export in `web/src/types/core.ts`). **Vocal mute (karaoke)** — *server-side ffmpeg, center-channel cancellation*: the fullscreen karaoke overlay's mic toggle flips `PlayerService.vocalsMuted`, and `player.component.ts` re-assigns `audio.src` through `ServerConfigService.streamUrl(id, token, { vocalsOff })`, appending `&vocals=off`. Server side, `streaming.ts` reads `?vocals=off` and **forces the transcode path even when `transcodeEnabled` is off** — filtering can only happen while re-encoding — as long as ffmpeg is present (no ffmpeg ⇒ graceful unfiltered passthrough, never a 500). `transcodeToFile` then applies `-af pan=stereo|c0=c0-c1|c1=c1-c0`: each output channel becomes the L−R difference, so anything mixed dead-center (typically the lead vocal) cancels while stereo-panned instruments survive. It's deterministic and dependency-free — imperfect (reverb/backing vocals leak; a mono downmix collapses toward silence), but this *is* the intended behaviour. `transcodeCacheKey` appends a `novox` marker **only** for the muted variant, so the filtered stream is its own cache entry while ordinary streams keep their existing keys (a deploy doesn't invalidate the whole transcode cache). Toggle state persists across tracks; position is preserved across the src reload via `restoredTime` (see [docs/web-ui.md](web-ui.md)). **History note:** this was gutted during the #134–#141 churn (the `vocalRemoval` param survived as a dead, eslint-disabled arg and the route never read `?vocals=off`), so vocal mute was a silent no-op until it was rewired — an earlier `stereotools` mid/side attempt was abandoned in favour of the `pan` cancellation above.
- **Guided acquire UX (raw network demoted)**: the catalog cards (album/EP/single, all routing to the same `huntCatalogAlbum` → `AlbumHuntModalComponent`) are the primary path; the raw network lane — peer bitrate/speed/queue stats, the Songs↔Folders toggle, and the full folder-tree `FolderBrowserComponent` — lives **only inside a collapsed "Advanced: browse Soulseek peers & folders" disclosure** (`data-testid="advanced-toggle"`), auto-opened only when there's no catalog hit so it stays the escape hatch, never the default (the acquirable hits surface in the blended Results list above it — see source-agnostic-acquisition.md). The album-hunt modal **leads with only the auto-selected best match** (`data-testid="hunt-best-match"`: "✓ Best match ready" + format/size/match%) and one Download action; the **full ranked peer list is opt-in** behind a collapsed **"Choose a different source (N found)"** disclosure (`data-testid="hunt-sources"`, holding the `hunt-candidate` rows + selection) so the common "just get it" case is a single tap, and its filters (FLAC/live/skew/min-match) are tucked behind a separate **"Explore more options"** `<details>` (`data-testid="hunt-options"`). A pasted/shared link is recognized in the same search omnibox as one more acquisition candidate — a **link-intent card** (chip auto-labelled YouTube/SoundCloud/Bandcamp/Spotify/Internet Archive/Link by `lib/link-intent.ts`, dispatched through `AcquireService.submit` — no backend choice exposed, no separate URL box or job list). → [docs/source-agnostic-acquisition.md](source-agnostic-acquisition.md)
- **Inline download lifecycle**: Search result cards show idle → blue progress wash + % → green "▶ Open in Library". Driven by `TransferService`; a `libraryDirty` signal tracks completed downloads (cleared on library page load, ignoring initial boot completions to prevent double-loading and disruptive auto-refreshes of active views). `TransferService` uses adaptive polling: 3 s when any transfer or acquire job is active, 30 s when idle. `kickPoll()` resets to fast mode immediately when a download is initiated. `AcquireService` mirrors the same first-poll guard via `hasRefreshed`: the initial `refresh()` (called by `LayoutComponent.ngOnInit`) silently baselines all existing terminal jobs without toasting; only subsequent running→done/failed transitions fire a toast — preventing the stale-replay flood of "added to library" messages on every app open.
- **Multi-user**: Shared music library (all users see all downloads). Per-user settings in bun:sqlite (`packages/api/src/db.ts`). First registered user becomes admin.
- **Service modes**: `embedded` (NicotinD spawns slskd as child process) or `external` (connects to a pre-existing slskd). Library/streaming stack is in-process — no music-server subprocess.
- **Auth flow**: NicotinD issues its own JWTs; holds auto-generated API key for slskd. Web player streams via `/api/stream/:id?token=` (JWT in query param). **Sliding sessions**: the JWT TTL defaults to **30 days** (`jwt.expiresIn`, `config/default.yml`) and the web silently renews it on every app boot — `provideAppInitializer` in `app.config.ts` fires `ApiService.refreshToken()` → `POST /api/auth/refresh` (`routes/auth.ts`, guarded by the existing `authMiddleware`, re-signs via `signJwt`) and swaps the token in via `AuthService.setToken()` (token-only, leaves username/role). So an active user effectively never hits the expiry wall and stops re-logging in daily; an actually-expired token 401s on refresh and the interceptor falls back to `/login`. **Share tokens are non-refreshable** (`/refresh` 403s on `share === true`) — they stay short-lived and read-only. **Device-bound sessions**: a JWT claimed through QR device pairing carries a `deviceId` pointing at a `paired_devices` row; `/refresh` 403s ("Device revoked") when the row is gone (row delete = revocation, the one stateful revocation mechanism), bumps `last_seen_at`, and threads `deviceId` into the re-signed token — see [device-pairing.md](device-pairing.md). The login page (`pages/login/`) is a fixed-palette glassmorphic card (indigo/fuchsia/teal aurora, theme-independent). **Form rhythm**: `<form class="space-y-5">` (20 px between username, password, error, and the **Sign In** submit) — `space-y-4` was too tight against the button, so the error block visually crowded the action; the wrapper is the single lever because every direct child of the form inherits it.
- **Route auth helpers + typed errors (`middleware/current-user.ts`)**: the repeated `const user = c.get('user'); if (user.role !== 'admin') return c.json({ error: 'Admin only' }, 403);` guard (21× in `routes/library.ts` alone) collapses to `requireAdmin(c)` — it returns the user and **throws a 403 `ForbiddenError`** (`@nicotind/core`, added alongside `AuthError`/`NotFoundError`/…) otherwise. `getCurrentUser(c)` is the typed one-call accessor for non-admin handlers. The central `errorHandler` maps any `NicotinDError` → `{ error, code }` at its `statusCode`; the library router now registers `app.onError(errorHandler)` on **itself** so a typed throw is mapped even when the router is mounted on a bare app (as the route tests do), not just under the global handler. This is the seed of routes-throw-typed-errors (vs. hand-rolled inline `c.json`); admin-denial bodies gained a `code` field (additive — clients key on the 403 status).
- **Artist page — tabbed, with a lazy Songs tab**: `artist-detail.component` presents **Albums | Singles & EPs | Songs** as a tab bar (`data-testid="artist-tab-{albums,singles,songs}"`, default = first populated tab) instead of stacked sections. The **Songs** tab is **lazy** (no fetch until first opened) and paginates via the library grid's IntersectionObserver pattern (`#songsSentinel`, `appendUnique`, `done`). It hits the new **`GET /api/library/artists/:id/songs`** (paginated; `sort`=newest|title|album via the pure `songOrderBy` whitelist; `starred=true` filter) and exposes a sort `<select>` + a Filters menu (`data-testid="artist-songs-filters"`). It supports a **strong multi-select with bulk actions** built on the existing `createSelection` (shift-click range) + an **extended `SelectionBarComponent`**: Play, Add to queue, Add to playlist, Download (offline) — each an **optional** output gated by a `can*` input (default off) so the playlist-detail usage is unchanged. (No Star bulk-action: the app has no star write-endpoint, so one wasn't invented.) **Admin delete parity**: because albumless files (loose songs that never grouped into an album) surface *only* on this Songs tab, it also offers deletion — a `canDelete` bulk button in the selection bar **and** a per-row destructive **Remove** action (`artistTrackActions`), both gated on `auth.role() === 'admin'` to match the hard backend gate on `DELETE /songs/:id` + `POST /songs/bulk-delete`. Removal prunes the local `songs` signal and records ids on `TransferService` (cross-view consistency), mirroring the album/genre-detail flow (`ConfirmDialogComponent` + `deleteError` banner). Without this the files were unremovable from any view.
- **Viewport-safe dropdown menus (`MenuPanelComponent`)**: filter/popover/context menus used a bare `absolute right-0`/`top-7` and could spill off a narrow viewport **or open *under* the fixed bottom chrome** (the mobile "track-row `⋯` menu near the list end hidden behind the mini-player/tab bar" bug). The reusable `components/menu-panel/` wraps a projected `[menuTrigger]` + `[menuPanel]`, renders the panel `position: fixed`, and positions it with the pure **`computeMenuPosition`** (`lib/menu-position.ts`) — anchor-aligns under the trigger, **flips above** when there's no room below, and always **clamps fully into the viewport** (so even a panel wider than the space pins to the edge margin). It also passes a **`bottomInset`** (the height of the fixed bottom chrome) into `computeMenuPosition`/`clampMenuPosition`, so the room-below calc and the bottom clamp both exclude the player/tab bar — the panel flips up or clamps *above* the chrome instead of landing behind it. The inset is measured at open time from the live rects of the chrome layers tagged **`data-bottom-chrome`** (mini-player div + `bottom-nav`) via **`measureBottomChromeInset`** (`lib/player-chrome.ts` — the shared DOM-reading wrapper over the pure `bottomChromeInset`, also used by `BottomChromeSafeDirective` so the two consumers can't drift on how the chrome is found), which ignores hidden (desktop tab bar, `height 0`) and slid-off-screen (idle mini-player, `top ≥ viewport bottom`) layers — no rem/safe-area recompute, it just reads what's rendered. The library **Filters** menu (`data-testid="library-filter-panel"`), the artist **Songs** filter, the downloads "View N albums" menu, and every **`TrackRowComponent`** `⋯` menu (`data-testid="track-row-menu"`, refactored off its old hand-rolled `absolute` panel) use it; the pure math (incl. `bottomInset`/`bottomChromeInset`) is unit-tested and an e2e asserts the panel's bounding box stays on-screen at 360px width.
- **Bottom-chrome stacking + full-screen scroll lock**: the mini-player and the mobile tab bar (`bottom-nav`) are both `z-50` — one plane — so a page-level modal backdrop (`z-50`, e.g. album-hunt) sits *under* both and they show/hide **together** (the old `z-40` bar got hidden by a modal while the player stayed visible). True full-screen sheets (Now Playing / add-to-playlist `z-[60]`, context menu `z-[70]`) still cover both. The Now Playing sheet pins the document via the ref-counted `ScrollLockService` (`services/scroll-lock.service.ts`: `overflow:hidden`+`overscroll-behavior:none` on `<html>` while ≥1 holder; nested overlays lock independently) so the backgrounded page can't scroll/overscroll behind it. The header's standalone download button was **removed** (Downloads is already a nav item) and its active-count badge folded onto the desktop "Downloads" nav link (`layout` `downloadCount()`; the mobile tab bar already carries it). The mini-player **grab "notch"** (`data-testid="player-grab"`) is now a solid full-opacity pill: it was invisible because its `bg-theme-muted` class **was never a registered utility** (only `bg-theme-{base,surface,surface-2,hover,accent,inverse}` existed), so it rendered transparent — `.bg-theme-muted` (→ `var(--theme-text-muted)`) is now registered in `styles.css`, which also fixes the settings status-dot that referenced the same class. Geometry/visibility contracts live in `lib/player-chrome.ts` + the `bottom-nav` docstring; both fixed layers (mini-player div + `bottom-nav`) carry a **`data-bottom-chrome`** attribute so popups can measure them at open time (`bottomChromeInset`, consumed by `MenuPanelComponent` — see "Viewport-safe dropdown menus") and never open behind them. Covered by `bottom-nav`/`layout`/`scroll-lock`/`player-chrome` unit specs and the `mobile-ux` e2e (grab-notch visibility — the e2e screenshots the **static grab element**, not the playing mini-player, whose moving seek bar never stabilizes and would hang `screenshot()`). **Full-screen modal backdrops reuse the same `bottomChromeInset` primitive (issue #367, hardened after the genre modal still overflowed)**: the Changelog modal and the artist genre-fix modal were both confirmed (screenshots) rendering their last content under the mini-player while a track was playing — every `fixed inset-0 z-50 flex items-center justify-center` backdrop centers its dialog against the *full* viewport with no awareness that the bottom ~144px is painted over by the higher-DOM-order, tied-`z-50` chrome. `BottomChromeSafeDirective` (`directives/bottom-chrome-safe.directive.ts`, `[appBottomChromeSafe]` on the backdrop element) fixes this generically rather than per-component: it measures every `[data-bottom-chrome]` layer via `measureBottomChromeInset` and sets the backdrop's `padding-bottom` to its own base padding (captured once via `getComputedStyle`, so it composes with whatever Tailwind padding each modal already had) **plus** the measured inset, turns on `overflow-y: auto` and `overscroll-behavior: contain` (so backdrop scrolling can't chain into the page behind — full `ScrollLockService` adoption for modals was considered and deferred; the ref-counted lock stays Now-Playing-only), and **publishes the inset as `--bottom-chrome-inset` on the backdrop**. The original one-shot init + `window:resize` measurement proved insufficient — the genre modal's radar charts land *async*, growing the panel after the directive ran — so the directive now re-measures on three triggers: `window:resize`, a **`ResizeObserver`** on the backdrop *and* its first child (the dialog panel; guarded `typeof ResizeObserver === 'undefined'` for jsdom, mirroring `tv-nav-group.directive.ts`), and **`transitionend` bubbling from a `[data-bottom-chrome]` layer** (the mini-player shows/hides via a transform *transition*, which never changes any observed element's box, so neither of the other triggers sees it). **The directive alone is not enough for a variable-height panel** — the canonical bounded-panel recipe is required on top of it, because an unbounded panel taller than the scrollport under `items-center` clips its top irrecoverably (a centered flex child overflows in *both* directions and the start-side overflow is unreachable in Chromium/WebKit):

  ```html
  <!-- Backdrop: NO items-center — the panel centers itself with m-auto, which
       centers when there is free space and collapses to 0 when there isn't. -->
  <div class="fixed inset-0 z-50 flex justify-center p-4 …" appBottomChromeSafe (click)="close">
    <!-- Panel: bounded by the live inset + the backdrop's own static padding
         (p-4 ×2 = 2rem here). Single-block forms use overflow-y-auto directly;
         header/body modals use flex flex-col overflow-hidden with an inner
         flex-1 min-h-0 overflow-y-auto body (the changelog-modal pattern). -->
    <div class="w-full max-w-md m-auto max-h-[calc(100dvh-var(--bottom-chrome-inset,0px)-2rem)] overflow-y-auto …" (click)="$event.stopPropagation()">
  ```

  A shared `<app-modal>` wrapper component was considered and rejected: 12+ bespoke backdrops would each need a migration + spec rewrite for zero behavioral gain over the directive + recipe. Applied sites after the sweep: the recipe on `artist-genre-modal` (the re-reported bug; its panel also carries `data-testid="artist-genre-panel"` for the geometry e2e) and `artist-identity-modal` (same latent shape); `album-hunt-modal` swapped its hand-rolled `max-h-[calc(100dvh-11.5rem)]` chrome guess (drifted from the real chrome) for the measured var and gained the directive; `layout.component.html`'s sign-out dialog gained the directive its `settings.component.html` twin already had; `feedback-detail-sheet` gained it for its `sm:items-center` desktop centering. Already-correct sites keep their markup: `changelog-modal` (`max-h-[80vh]` + inner scroll), `metadata-fix-modal` (`max-h-[85vh]`), `confirm-dialog`, `artist-image-menu`'s album picker, the 3 inline `admin.component.html` dialogs, `settings.component.html`'s sign-out dialog. `add-to-playlist` (`z-[60]`) and `track-info-sheet` (`z-[90]`) are **deliberately above the chrome plane** and correctly have no directive. Covered by `bottom-chrome-safe.directive.spec.ts` (incl. a spec-local ResizeObserver stub — never a global polyfill, which would mask the jsdom guard) and a real-geometry e2e in `genre-radar.spec.ts` asserting the playing-state panel's box clears the measured chrome top.
- **Downloading albums suppressed from listing**: `GET /api/library/albums`, `GET /api/library/singles`, and `GET /api/library/artists/:id` exclude albums that are actively downloading (matched via `normalizeForGrouping`). Suppression keys on the **union** of (a) active `album_jobs` rows and (b) **in-flight slskd transfers** — the latter (pure `services/transfer-group-keys.ts` `transferGroupKeys`, parsing each active transfer dir's last two path segments → `albumGroupKey`, only for dirs with a non-completed file) covers **raw folder-browser / per-track grabs that never create a job row**, which used to surface mid-download (the Ultraviolence "5 copies showed while downloading" bug). The transfer fetch is cached ~4 s (`activeTransferKeys`, module-level, reset for tests via `__resetDownloadSuppressionCache`) so listing requests don't hammer slskd, and degrades to album_jobs-only when slskd is absent/unreachable. The paginated endpoints (`/albums`, `/singles`) apply the exclusion **inside the SQL `WHERE` (`downloadingExclusion()` in `routes/library.ts`, an `id NOT IN (…)` fragment), not as a post-`LIMIT` JS filter** — filtering after `LIMIT/OFFSET` shrank each page below its requested size, so the web's offset-accumulating grid (`library.component.ts`) re-fetched already-shown rows and rendered the same album 2–3× (and tripped `done` early, truncating the grid). `downloadingExclusion()` has a zero-cost fast path when nothing is downloading. The card reappears once every copy clears `active`/in-flight (slskd times out stuck transfers; the user can also cancel). `DownloadWatcher.start()` seeds `knownCompleted` from `completed_downloads` at boot so container restarts don't replay history.
- **ServiceReview: one resource, one polling lifecycle (consolidates every Admin read-only telemetry signal)**: a single `GET /api/admin/review` resource (`packages/api/src/routes/review.ts`, admin-only, mounts under the existing `/api/admin/*` blanket auth + an inline admin gate) replaces the page's prior 8 independent fetchers (`getStatus`/`getScanStatus`/`getUpdateCheck`/`getBackups`/`getAuditLog`/`getProcessing` + `getIncompleteJobs`/`getUntracked`, plus the new hardware metrics). **One round-trip per poll**, **one `collectedAt` timestamp** so the UI reasons about staleness coherently, and **one error policy**: every sub-fetch is wrapped in `safe(errors, label, fn, fallback)` (`try`/`catch` + log into `errors[]` + return the fallback) so a 503 from Lidarr, an absent `dataDir`, a missing `slskd`, or an SQLite lock degrades **that one field** instead of dropping the whole response. **Sub-fetches are individually injectable** via `ReviewRoutesDeps.subFns` (`collectMetrics` / `systemStatus` / `scanStatus` / `analysisStatus` / `indexSongCount` / `updateCheck` / `backupsList` / `processingSummary` / `incompleteJobCount` / `untrackedCount` / `orphanRows` / `auditTail` / `incompleteJobs` / `untracked`) — `routes/review.test.ts` drives every degraded path deterministically by replacing each entry. **Slices are gathered by name, not by position (issue #274)**: the handler used to destructure 13 names positionally out of one `Promise.all([...])`, so adding a slice meant editing the name list and the array in exact lockstep — and a mismatch was invisible to the type-checker wherever two slices share a type (`incompleteJobsCount`/`untrackedCount` are both `number`; `incompleteJobs`/`untracked` are both object arrays), so a swap type-checked cleanly and produced a wrong Admin panel. The gather now goes through the tiny `allNamed()` helper (`Promise.all` over an object) and destructures **by name**, so the same mistake is a compile error; verified by deliberately swapping two keys and confirming `tsc` rejects it. - **Closing issues when work merges (`check-shipped-issues.ts`, issue #257)**: `Closes #N` in a **PR body** is an *action* GitHub honours on merge; `(#N)` in a **commit subject** is only a *reference* — it links, and the issue stays open forever. The repo used both interchangeably, so work shipped while its issue stayed open: **six** found in one audit, and **five more** (#261–#265) after that, all shipped in `fab2a91`/v0.1.274 while sitting `OPEN`. The cost is that an open list containing finished work makes every triage pass re-derive context for work that's done, and it *hides the real remaining scope* — the worst variant being a partly-done issue whose only accurate scope record was a prose line in CLAUDE.md, so it looks bigger than it is and keeps getting skipped. Two mechanisms: `.github/PULL_REQUEST_TEMPLATE.md` prompts for the `Closes #`/`Refs #` line and explains the distinction inline (the repo had **no** PR template at all), and `bun run check-shipped-issues` reports open issues referenced by a shipped commit, flagging the loudest case — a commit carrying a *closing keyword* whose issue is still open, meaning the keyword lived only in a commit body and never the PR body. It is **deliberately a report, not a gate**: a commit can legitimately reference an issue without resolving it, and the real backlog proves it — `#220`'s only hits are a branch name (`claude/github-tasks-211-220-…`) and a literal "scaffold #220". A hard failure on that heuristic would be wrong often enough to get muted, so it lists candidates a human confirms. Partial work takes `Refs #N` plus a scope comment rather than a close.
- **JSON config duplicate-key gate (`check-json-configs.ts`)**: `JSON.parse` accepts duplicate keys and silently keeps the **last** one, which makes a whole class of damage invisible to every other check — most realistically from a merge resolved by keeping both sides of a conflict, which is the natural resolution for the additive edits these files actually get. **Found empirically, not hypothesised**: test-merging the open PR queue produced two `"typecheck"` entries in `package.json`, and the *second* won — silently discarding the Angular-template type-check that the PR introducing it exists to add. `JSON.parse` called that document valid; only Bun's own parser warned, in passing. `bun run check:json` (CI) scans `package.json`, every workspace manifest, `angular.json`, `ngsw-config.json` and the i18n catalogs (a duplicate there silently drops a translation, and the base catalog is meant to be a clean artefact a provider can import); tsconfigs are excluded because they are JSONC. **Detection is a hand scanner, not a `JSON.parse` reviver** — the reviver *cannot* see duplicates, because the parser resolves them while building the object and calls the reviver once per *surviving* member; the reviver version reported zero duplicates on a document that had them, and a test established that before it shipped. A gate rather than a report (unlike `check-shipped-issues.ts`): a duplicate key is never intentional, so there is no false-positive class to cry wolf with.

- **Additive schema migrations (`addColumnIfMissing`, issue #275)**: `applySchema` runs on **every boot**, so it must be idempotent — but the 38 migrations that expressed that were each a hand-written `try { ALTER TABLE … ADD COLUMN … } catch {}`. The swallow was unconditional: it treated "duplicate column name" (expected) and a genuine SQL error in the `ALTER` (a typo'd type, a bad default) **identically and silently**, so a malformed migration was indistinguishable from an already-applied one and only surfaced much later as a mysteriously missing column. `addColumnIfMissing(db, table, column, decl)` checks `PRAGMA table_info` instead, which turns "already there" into a **condition** rather than an **exception** — so a real migration bug now throws loudly at boot, which is the behaviour change worth having (pinned by a test asserting a malformed declaration throws). It **returns whether it added the column**, so the two one-time backfills (`album_artist`, `album_artist_id`) stay gated on the add exactly as the old try-block gated them — under the old shape a later boot threw on the `ALTER` and skipped the `UPDATE` with it, so re-running the full-table `UPDATE` every boot would have been a *new* cost, not a preserved one. **Scope**: additive columns only. The three table-`RENAME` rebuild migrations (`acquire_jobs`, `share_tokens`, `library_albums` CHECK-constraint relaxations) and the one non-`ALTER` `try` (the `playlist_visibility` backfill, whose catch tolerates something else entirely) are deliberately untouched. **Never a destructive migration** — the library tables are rebuilt wholesale by the scanner, and the restore path is a documented manual DB swap ([backup-restore.md](backup-restore.md)), so there is no down-migration machinery to lean on. Verified against prod: all 46 managed columns already exist there, so the next boot performs 46 `PRAGMA` reads and **zero** `ALTER`s (which also proves the 38-site conversion didn't mistype a column name — a typo would have shown as missing).
